This is a subclass constructor that demonstrates the danger of calling an overridable method from a constructor. The constructor initializes the superclass via super(), then calls show() (which dispatches to the subclass override), and only after that does it set its own field n. At the moment show() prints, the subclass's own fields are still at their default values, while the superclass fields already hold their initialized values.
- B is a subclass of some superclass (name unknown from this snippet). Both the superclass and B declare fields named s and n. B's fields shadow (hide) the superclass ones.
- The constructor B() first calls super(), which runs the superclass constructor and sets the superclass's s and n to whatever values that constructor assigns.
- After super() returns, the constructor calls show(). Because show() is not static and not final, Java uses dynamic dispatch: it looks up the actual object's class (B) and calls B's override.
- Inside B.show(), the bare names s and n refer to B's own fields (the shadowing ones). The expressions super.s and super.n refer to the superclass's fields.
- After show() returns, the constructor continues with n += 100, which modifies B's field n. But show() has already printed, so this change is not reflected in the output.
- The @Override annotation on show() confirms the superclass also declares a show() method; B's version replaces it for dynamic dispatch.
- With the standard java.lang.System, System.out is a java.io.PrintStream for text output. print writes its text; println also ends the line. These are standard-library tools, while classes declared in this selection are your own code.
1. The B() constructor is invoked on a new B object. Before any of B's own code runs, the JVM must first initialize the superclass part of the object.
2. super() calls the superclass constructor. This sets the superclass's fields s and n to whatever values that constructor assigns. We don't see the superclass code, so we don't know those exact values. After super() returns, the superclass portion of the object is fully initialized.
3. The constructor body now calls show(). This is a virtual (dynamic) method call. The runtime type of the object is B, so the JVM looks up B's show() method and calls it. The superclass's show() is NOT called here.
4. Inside B.show(), the expression s + n + super.s + super.n + " " is evaluated left to right. The bare s refers to B's own field s, which has NOT been initialized by the constructor body yet (we haven't reached n += 100, and any field initializers in B's class body that come after the constructor in source order also haven't run for this object — actually, field initializers DO run before the constructor body, but since we don't see them, we assume defaults). So s is at its default: 0 if numeric, null if String/object. Similarly, n is at its default. super.s and super.n are the values set by the superclass constructor in step 2. The + operator concatenates them all into a single string (converting numbers to their text form, null to the text 'null').
5. System.out.print outputs the concatenated string. The exact characters depend on the unknown types and initial values. The pattern is always: [B.s default] [B.n default] [super.s value] [super.n value] followed by a space. For example, if both s fields are int (default 0) and both n fields are int (superclass set to some value like 5), the output might be '0055 ' — but this is just an illustration; we cannot confirm actual values without the superclass code.
6. Control returns to the B() constructor. The next statement n += 100 executes. This reads B's field n (currently at its default, e.g., 0), adds 100, and stores the result back into B's field n. From this point on, B's n is 100 (or default+100). But show() has already printed, so this value will not appear in any output from this constructor call unless show() is called again later.
The exact printed characters depend on the superclass's field types and initial values, which are not shown. The format is always: [B's s] [B's n] [superclass's s] [superclass's n] (space-separated), where B's s and n are at their default values (0 or null) at the time of printing, and the superclass's s and n are whatever super() set them to.
- The most important pitfall: B's own fields s and n are still at their default values (0 for int/long/etc., null for String/object) when show() runs from the constructor. Any initialization you put in B's constructor body AFTER the show() call will NOT be visible to show(). This is why calling overridable methods from constructors is considered dangerous.
- super.s and super.n DO have their proper values because super() has already finished running before show() is called. So the superclass fields are 'real' and the subclass fields are 'empty' at print time.
- The line n += 100 runs AFTER show() returns. It changes B's n for future use, but the print has already happened. If you expected the printed n to include the +100, you'd be wrong.
- If s is a String type in B and is null (default), the printed output will contain the literal text 'null' where s appears. If n is an int and defaults to 0, it prints '0'.
- The @Override annotation does not change behavior; it only causes a compile-time error if the superclass didn't actually declare a matching show() method. At runtime, the dispatch works the same regardless.
